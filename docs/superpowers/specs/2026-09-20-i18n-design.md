# Internationalisation: English and Portuguese

Sub-project 2 of 2. Builds on the visual redesign (`2026-09-20-visual-redesign-design.md`): the `.btn`, `.win` and palette-picker components, the typewriter effect and the shell-style 404 page all exist and are translated here.

## Goals

- Serve the whole site in English and Portuguese: UI, boot lines, whoami page and all 8 TIL posts.
- Real per-language URLs, shareable and indexable.

Non-goals: automatic redirect on browser language, more than two languages, translated menu command names (`boot`, `whoami`, `TIL` stay).

## Hugo 0.166 facts this design relies on (checked in a throwaway project)

- Language config uses `label` (not the deprecated `languageName`) and `locale`.
- `site.Languages` and `.Language.LanguageName` are deprecated (they print `WARN`, which the check script treats as a failure). Use `hugo.Sites` (each item has `.Language.Lang`, `.Language.Label`, `.Language.Locale`, `.Home`) and `.Language.Label`.
- A menu defined at the config root applies to every language; `absLangURL` prefixes `/pt` automatically for Portuguese pages.
- Language-level `params` replace the root value for that language, so boot lines live only in `[languages.<lang>.params.boot]`.
- `hugo --printI18nWarnings` reports missing keys as `WARN  i18n|MISSING_TRANSLATION|<lang>|<key>`.

## Design

### Configuration (`hugo.toml`)

- `defaultContentLanguage = "en"`, `defaultContentLanguageInSubdir = false`. English stays at `/`, Portuguese at `/pt/`. The root `locale` key moves into the language blocks.
- `[languages.en]`: `label = "English"`, `locale = "en"`, `weight = 1`. `[languages.pt]`: `label = "Português"`, `locale = "pt-BR"`, `weight = 2`.
- Menu stays as one root `[menu]`: the names are the same in both languages and `absLangURL` handles the prefix.
- Boot lines move from `[params.boot]` to `[languages.<lang>.params.boot]` (a list per language). Proper names (Go, Java, Python, Full Cycle, FIAP) stay as they are.

### Content

- Sibling files by language suffix: `content/_index.pt.md`, `content/about/index.pt.md`, `content/til/_index.pt.md` and `content/til/<slug>.pt.md` for each of the 8 posts (`gcp-cloud-monitoring-agent`, `go-confinement-pattern`, `go-deadcode`, `go-errgroup`, `go-file-naming`, `go-sorting`, `mongo-crud`, `using-katex`).
- Front matter: `title` is translated. `date`, `tags` and `math` are copied unchanged so both languages stay in sync. Section pages do not copy `aliases`.
- Body: prose translated into pt-BR (informal `você`, first person where the original uses it). Fenced code blocks are copied byte for byte, comments included. Identifiers, commands, URLs, tag names and technical terms without a common Portuguese form (goroutine, mutex, errgroup, pipeline, cluster) stay in English.
- I write the translations. The site owner reviews the Portuguese before merge.
- `scripts/check-translations.py` fails the check suite if an English page has no `.pt.md` sibling, if `date`, `tags` or `math` differ, or if the fenced code blocks differ.

### UI strings

- New `i18n/en.toml` and `i18n/pt.toml` with identical key sets, used via `{{ i18n "key" }}` in the partials (`printf (i18n "key") value` for strings with a number or name).
- Covered: palette popup title, aria-label and palette display names (`dark`/`light`/`pink` become `escuro`/`claro`/`rosa`); sidebar window titles (`connect` becomes `conectar`, `latest_til` becomes `ultimos_til`; `status` and `stack` stay), status labels (`> location:` becomes `> local:`, `Brazil` becomes `Brasil`), social and stack aria-labels and link titles, portrait alt text, boot log aria-label and the built boot lines (`Indexed %d TIL entries.`, `Reached target Graphical Interface.`, uptime), the language picker title and label.
- `assets/js/theme.js` shows the selected palette's name by copying the text of the matching option button, so no user-visible text is hard-coded in JS. `typewriter.js` has no strings.
- TIL list date format `dd/mm/yy` already fits both languages.

### Language picker

- The header button shows the current language (its flag and code, for example `en`) and opens a small window, like the palette popup, titled `language` / `idioma`, that lists every language with its flag and name (`English`, `Português`), the current one marked with `>`. Nothing switches until a language is chosen.
- Choosing a language goes to the current page's translation (`.Translations`); if there is none, to that language's home (`.Home.RelPermalink`). On the 404 page (one file for every URL) it always goes to the language's home. Choosing the current language stays on the page.
- Built as a native `<details>` with the `<summary>` styled as a `.btn`, so it opens without JavaScript; `assets/js/lang-picker.js` only adds the closing behaviour (Esc returns focus to the button, click outside, tabbing out). Opening the palette popup counts as a click outside, so at most one popup is open.
- Flags are inline pixel-art SVGs (a 16x11 grid drawn at 2px per pixel, `crispEdges`, fixed colours so they do not follow the palette): United States for `en`, Brazil for `pt`. They are decorative (`aria-hidden`); each language row's accessible name is the language name, and the button's label starts with its visible text (`en: choose language`).
- Loops `hugo.Sites` (never the deprecated `site.Languages`). No redirect on `navigator.language`; the choice is the URL. The palette choice persists in `localStorage` across languages.
- The unused `layouts/partials/lang.html` is deleted.

### 404 page

- GitHub Pages serves only the root `/404.html` for every missing URL, so one page must serve both languages. `layouts/404.html` renders one `.notfound` block per language, from a language-neutral `data/notfound.toml` (`en` and `pt` tables: the shell error text and the placeholder path); links use `/` for English and `/pt/` for Portuguese.
- The inline script (which already fills in the requested path) keeps the block matching the URL (`/pt/...` shows Portuguese, everything else English) and removes the other from the DOM, so the typewriter effect does not spend time on hidden text. With JavaScript off, both blocks show, English first.
- The commands (`cd`, `ls ~`) stay English, as shell commands do; only the error line is translated (`Arquivo ou diretório inexistente`).

### SEO

- `<html lang>` uses `site.Language.Locale` (`en`, `pt-BR`).
- `head.html` adds `<link rel="alternate" hreflang="…" href="…">` for each translation of the page, plus `hreflang="x-default"` pointing to the first language (English).

## Testing

- `hugo --gc --printI18nWarnings` builds clean for both languages, no missing-key or deprecation warnings (the check script's build step runs with the flag).
- Check script groups assert: both languages configured, identical i18n key sets, `/pt/` pages exist with `lang="pt-BR"`, no English UI strings on Portuguese pages and vice versa, hreflang links, the switcher link on both languages, the 404 carries both languages, translations in sync (`check-translations.py`).
- Playwright per language and palette at desktop and phone widths: Portuguese strings fit their buttons, sidebar titles and boot log; header still fits with both buttons; switcher on a translated page and on a page with no translation; `/pt/nada` and `/nada` 404s; typewriter works on Portuguese pages.
